# AI Audio Editor

An AI-enabled, browser-based audio editor that can understand a timeline and automatically apply sound effects based on the content.

Instead of manually searching for audio clips and placing them on a timeline, you can describe what should happen and let an AI agent modify the underlying project structure.

> **Demo note:** To keep the demo short, the video shows the final audio output alongside the editor interaction rather than playing through the entire timeline. The audio at the end is the actual output generated by the editor.

## Overview

This project started as an experiment in building a fully browser-based audio editor and exploring how AI could be integrated into a creative application.

The editor provides the core workflow you'd expect from a timeline-based audio tool:

* Add and arrange audio clips
* Trim clips
* Loop audio
* Apply fades
* Mute clips
* Preview the timeline
* Export the final audio
* Process audio using `ffmpeg.wasm`

The interesting part is the architecture behind the editor.

The **entire timeline is represented as structured JSON**, which acts as the source of truth for the project.

That same representation is used by the UI, audio engine, FFmpeg processing layer, and AI agent.

This makes the project editable not only through the UI, but also programmatically.

---

## Why Structured Projects?

A traditional creative application might look something like:

```text
Human
  ↓
UI
  ↓
Tool
```

The user interacts with buttons, menus, sliders, drag-and-drop operations, and other UI elements to manipulate the project.

This project explores a different approach:

```text
Human
  ↓
AI Agent
  ↓
Structured Project
  ↓
Tool
```

Instead of asking an AI agent to operate the editor like a human — clicking buttons, dragging clips, and navigating menus — the agent can work directly with the underlying project representation.

For example, a user could describe a sequence such as:

> Add a whoosh when the object enters the frame, a hit when it lands, and ambient background audio throughout the scene.

The agent can interpret that instruction and modify the timeline JSON accordingly.

The editor then renders and processes the updated project.

At a high level, the system looks like this:

```text
                   ┌─────────────────┐
                   │      Human      │
                   └────────┬────────┘
                            │
                            ▼
                   ┌─────────────────┐
                   │    AI Agent     │
                   └────────┬────────┘
                            │
                            ▼
                   ┌─────────────────┐
                   │ Structured JSON │
                   │  Project State  │
                   └───────┬─┬───────┘
                           │ │
              ┌────────────┘ └─────────────┐
              ▼                            ▼
      ┌─────────────────┐         ┌─────────────────┐
      │   Audio Engine  │         │    React UI      │
      └────────┬────────┘         └─────────────────┘
               │
               ▼
      ┌─────────────────┐
      │   FFmpeg.wasm   │
      └────────┬────────┘
               │
               ▼
        Final Audio Output
```

The JSON project representation is the central layer connecting everything together.

## Timeline as JSON

The timeline is represented as structured data rather than being tied directly to the UI.

Conceptually, a project might look like:

```json
{
  "tracks": [
    {
      "id": "track-1",
      "clips": [
        {
          "id": "clip-1",
          "source": "ambient.wav",
          "start": 0,
          "duration": 30,
          "volume": 0.8,
          "fadeIn": 1,
          "fadeOut": 2
        }
      ]
    }
  ]
}
```

The exact schema can evolve, but the important idea is that the project is **structured, serializable, and independent from the UI**.

That means the same project representation can be:

* Rendered by React
* Played by the browser audio engine
* Processed by FFmpeg
* Modified by an AI agent
* Saved and loaded
* Potentially shared between different tools

## AI Sound Design

The AI layer is designed to operate on the project rather than directly on the editor interface.

Given a description of what should happen, the agent can reason about the timeline and apply appropriate changes.

For example:

```text
User:
"Add a short whoosh as the camera moves quickly,
then add an impact when the object hits the ground."
```

The agent can translate that intent into project operations such as:

```text
1. Identify the relevant moments
2. Select appropriate sound effects
3. Add clips to the timeline
4. Position them at the appropriate timestamps
5. Adjust duration / volume / fades
6. Return the updated project
```

The UI doesn't need to know whether those changes were made manually or by the AI.

It simply renders the resulting project.

## Local LLMs

The AI layer is designed to be flexible around the underlying model.

A local model can be selected depending on:

* Model capability
* Available hardware
* Latency requirements
* Context length
* Tool-use capabilities
* Desired level of reasoning

This makes the architecture suitable for experimentation with different local models without fundamentally changing the editor itself.

## MCP Exploration

One of the original goals of the project was to explore connecting the editor to AI through **MCP**.

Because the editor runs inside the browser, however, connecting an external AI client directly to the application introduces additional complexity.

One possible architecture would involve something like:

```text
AI Client
    │
    ▼
   MCP
    │
    ▼
WebSocket / Communication Layer
    │
    ▼
Browser Application
    │
    ▼
Structured Project
```

This is certainly possible, but it introduces another communication layer between the AI client, browser, and editor.

For this experiment, embedding the AI agent directly into the editor provides a simpler architecture:

```text
Browser Application
        │
        ├── Editor
        ├── Audio Engine
        ├── FFmpeg
        │
        └── AI Agent
              │
              ▼
           Project JSON
```

This keeps the agent close to the data it needs to manipulate.

## Core Design Principle

The main idea behind this project is simple:

> **Make the project itself the interface.**

Instead of building an AI integration around every UI interaction, expose a structured representation of the underlying creative project.

That allows an AI system to work at a higher level of abstraction.

For example:

```text
Traditional automation:

AI → Click button
   → Find input
   → Drag clip
   → Adjust slider
   → Click export


Structured project approach:

AI → Modify project
   → Render
   → Process
   → Export
```

The second approach potentially makes the AI integration significantly more robust because the agent isn't dependent on the visual structure of the application.

## Why This Is Interesting

The project started as an attempt to add AI capabilities to an audio editor.

It ended up raising a broader architectural question:

**What happens when creative applications are designed around structured, machine-readable project files from the beginning?**

If the project state is structured enough, an AI agent doesn't necessarily need to learn how to use the application.

It can work directly with what the application represents.

That could potentially extend beyond audio into other creative domains:

```text
Audio
  └── Timeline JSON

Video
  └── Project JSON

Animation
  └── Scene / Timeline JSON

Image Editing
  └── Layer / Document JSON

3D
  └── Scene Graph JSON

Music Production
  └── Tracks / Clips / Effects JSON
```

The UI becomes one way of interacting with the project rather than the only way.

## The Bigger Idea

This project is less about building an AI that can operate an audio editor and more about exploring a different way to architect creative software.

Instead of:

```text
Human → UI → Tool
```

the goal is to make this possible:

```text
Human → AI Agent → Structured Project → Tool
```

When the underlying project is structured, the AI doesn't need to imitate a human interacting with the UI.

It can operate on the same representation that the application itself uses.

That separation between **intent, project state, and rendering** could make AI integration much more natural — not only for audio editors, but potentially for creative software in general.
